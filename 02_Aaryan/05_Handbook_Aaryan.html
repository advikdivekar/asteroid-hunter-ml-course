Pitfalls

  • Saying "we downloaded the data" without saying how it was chosen and how it was split.
  • Confusing the reference image (old, deep) with the science image (tonight).
  • Forgetting that reference = science - difference is computed (ZTF already aligned and blurred it).

  • Treating NaN as 0 without masking: its edge becomes a fake "detection".

1. Problem formulation (3 marks: write this section well)

The task. Given several consecutive 30-second exposures of the same patch of sky, find the objects that move across them (asteroids), decide which detections are real, and tell the known ones from the unknown ones. Input: a night of difference images of one CCD quadrant (5 frames, about 7,800 blobs each). Output: a ranked list of tracks with a score and a known/unknown flag. Why it is hard: (1) 97% of blobs are junk; (2) asteroids that matter are faint, barely above the noise; (3) there is no ground truth in real images (we must create labels); (4) the telescope pointing shifts between exposures; (5) public catalogues themselves have position errors. Why ML: junk comes in many shapes (dipoles, cosmic rays, edges, noise); a CNN learns them from examples where rules cannot; tree models combine many weak track clues; and the rest is physics (matched filter, linking, stacking), not learning. Success is measured by completeness (how many planted fakes are recovered, by brightness) at a fixed number of false alarms, depth (the brightness where 50% are recovered), known asteroids recovered, and unexplained alarms per night. Accuracy is not used (3% positives). A baseline is required: logistic regression on six numbers per blob (AP 0.780). Every later model must beat it. Scope and honesty: public data only; one field mostly; a research pipeline, not a discovery claim. Origin: a post claimed a planet candidate in old Kepler data found with AI-assisted code. We checked it (kepler_post_check.md): the 13.77-day signal matches the confirmed planet Kepler-169 e (chance of the period match about 1 in 350), simple blending cannot make a dip as deep as claimed (0.0685% maximum vs 0.24% reported), and the decisive test is whether the dips fall at that planet's transit times. We kept the habits: cross-match, quantify the coincidence, name the decisive test.

2. The data

2.1 Where it comes from

ZTF images, served by IRSA. For every exposure: science image (38 MB), mask (19 MB), difference image (7 MB, compressed), PSF (6 KB). The difference image is science minus a deep reference that ZTF has already resampled and blurred to match, so reference = science - difference gives us the reference on the same grid for free.

2.2 Metadata first

A single web query returned a table of 1,552 exposures of our quadrant (field 618, CCD 3, quadrant 4): 898 r-band, 478 g-band, 176 i-band; 16.4% had quality flags (infobits != 0), which we exclude. Choosing nights from this table costs seconds; downloading the wrong 3.5 GB costs an hour. Linking needs several exposures on the same night: only 40 nights had at least 4 good r-band frames.

2.3 The split (the most important design decision of the data stage)

split nights median seeing median depth
train 8 1.86 px 20.32
validation 2 2.08 px 19.85
test 1 (2019-02-08) 1.60 px 21.08
A holdout night (2022-06-17) was added later for the scoreboard. The test night is the best night (sharp, deep, near opposition): the most promising for discovery, so it must not be tuned on. It is also a deliberate distribution shift: expect fainter sources than the model has seen much of.
Why a config file: configs/acquire.yaml fixes the split before modelling, so it cannot drift after disappointing results. check_split_leakage must return an empty list for every pair of splits.

2.4 The downloader (engineering rules you can explain)

  • Idempotent: running it twice equals running it once (existing files are skipped).
  • Atomic: a file is written as .part and renamed only when complete; a crash cannot leave a half file that looks finished.
  • Retry with growing waits (20 s, 40 s, 60 s...) when the archive says 503 (busy); it did, twice, and recovery worked.
  • 404 handling: some exposures lack a product for good (e.g. the subtraction failed); they are recorded in missing_exposures.csv and skipped everywhere.
  • Total: 11 nights x 5 frames + 1 reference = 220 files, 3.55 GB, nothing missing.
  • Provenance: the metadata table is cached (metadata__000618.csv), so re-runs work offline and are repeatable even if the archive changes.

2.5 The mask

Each pixel has 16 yes/no flags. We mask: satellite track (0), bad responsivity (2, 3), noisy (4), spike (7), saturated (8), dead (9), NaN (10), halo (12). We do not mask the "ghost" bit (5): ghosts cover about 4% of the chip, masking them would hide real asteroids that cross them, and the model can learn what ghosts look like. We read the meaning of each bit from the mask file's own header (BIT00...BIT15) instead of guessing.

3. Preprocessing: what load_exposure does

  1. Read the difference image, mask and PSF (and the science image if present).
  2. Build the bad-pixel mask: ZTF flags + pixels near saturated stars (grown) + NaN pixels. About 6-12% of a difference image is NaN (regions that could not be subtracted); one example frame has 11.9% masked.
  3. reference = science - difference.
  4. Return images, mask, PSF (normalised to sum 1), header, time, zero point, gain. Background and noise (estimate_background): the sky level varies slowly (moonlight, clouds). SEP measures the sky in 64 x 64 boxes ignoring stars and interpolates a smooth map; the noise map is the scatter in each place. Robust noise = 1.4826 x MAD, because a bright blob must not inflate it (a plain standard deviation on our example frame was 15.1 vs 8.0 robust). Sky coordinates (WCS): pixel <-> RA/Dec. Pointing shifts between exposures; the "common grid" (Satvik's linking) depends on this.

4. Detection and exploration (EDA)

4.1 extract_sources

Mark NaN/bad pixels, subtract background, smooth with a star-shaped kernel (matched filter: random noise averages down, a star-shaped signal does not), keep groups of at least 5 connected pixels at least 2 sigma above the noise, measure flux in a 3-pixel circle, SNR = flux / flux error. Only positive blobs are kept: an asteroid is in tonight's image, not in the reference.

4.2 The threshold surprise (one training frame)

threshold detections median size
1.5 sigma 6,141 11 px
2.0 sigma 7,764 6 px
3.0 sigma 731 8 px
5.0 sigma 334 9 px
At 1.5 sigma neighbouring noise peaks touch and merge into big blobs, so there are fewer detections and a faint asteroid next to a noise blob gets swallowed. A rule of thumb is a start; measuring is better. 2 sigma was chosen and later checked with injections.

4.3 Most detections are noise, and that is fine

At 2 sigma about 7,800 detections per frame, only 173 with SNR > 5 (see 07_Diagrams/03_preprocessing_funnel.svg). Detection is tuned for completeness (miss nothing); the CNN (Paras) is tuned for purity. Science image: 1,950 sources at 5 sigma; difference image: 334 (about 6x fewer).

4.4 The stamp zoo (what the three panels show)

See Paras's triplet_stamp.svg: a real object appears in science and difference but not in reference; a bad subtraction shows a star in both and a dipole in the difference; a cosmic ray is a sharp spike narrower than a star; noise is a faint speck; a masked edge is a step.

4.5 The combinatorics problem

5 frames x about 8,000 blobs: one blob per frame in every combination is 8,000^5 = about 3 x 10^19 possible tracks. Two fixes later in the pipeline: the classifier removes most junk first, and the linker only tries combinations consistent with straight-line motion.

5. The leakage audit (your signature story)

Our very first dataset (legacy/tracklets.csv, 3,530 rows, 50% real) gave 99.8% accuracy, then 100% with log features. A perfect score is a symptom; we asked what would have to be true of the data.

Kind What it is Ours
Target leakage a feature contains the answer mag, true_rate, true_angle filled for every planted fake and for no bogus row
Group leakage train and test share a source all tracklets came from the same 4 images
Shortcut learning classes differ in an easy unreal way random bogus tracklets had residual >= 222.7 px; real ones <= 2.6 px, so one rule separates them
Distribution shift deployment differs from training test night sharper and deeper
The experiment: trained on easy data and tested on easy data: 100%; trained on easy data, tested on realistic near-miss tracklets: 50% (a coin flip); trained on realistic data (real + near misses), tested on realistic: 99%.
Hard negatives teach most. By how far one detection is moved off the line: 3-10 px -> 99%; 1-3 px -> 96%; 0.5-1.5 px -> 89% (a source 1 px off a line is nearly invisible to position-only features, which is why Paras's CNN looks at pixels).
Rules that came out of it: features must be measurable on new data; split by night; derived examples go with their source; negatives must be realistic.

Aaryan: viva questions and model answers

A. Problem formulation

1. What problem does the project solve? Finding moving objects (asteroids) in consecutive telescope images, deciding which detections are real, and separating known from unknown ones, with an honest measurement of how deep and how reliable the search is.

2. What are the input and output of the whole system? Input: a night of difference images for one CCD quadrant (5 frames). Output: a ranked list of tracks with a score and a known/unknown flag, for a human to examine.

3. Why is the problem hard? Only about 3% of blobs are real; the interesting asteroids are barely above the noise; real images have no ground truth; the telescope pointing shifts between exposures; and the catalogues we compare with have position errors.

4. Why use machine learning? Junk blobs have many shapes that rules cannot capture, so a CNN learns them from examples; trees combine many weak track-level clues. The rest (matched filter, linking, shift-and-stack) is physics and search.

5. How do you measure success? Completeness (fraction of planted fakes recovered) by brightness, depth (50% completeness magnitude), known asteroids recovered, unexplained alarms per night, and for classifiers recall at a fixed false-alarm level and average precision. Not accuracy.

6. Which paper does the project relate to? The closest is Duev et al. 2019 (real-bogus classification for ZTF with a CNN); also Mahabal et al. 2019 (ML for ZTF), Whidden et al. 2019 (shift-and-stack on GPUs), Masci et al. 2019 (ZTF data processing). Say what we replicated (a CNN on science/reference/difference triplets) and what we changed (31x31 stamps, our own labels).

7. What was the origin of the project and what did you check? A post that claimed a planet candidate in old Kepler data. We checked it: the period matches a confirmed planet (Kepler-169 e, 13.7671 days; chance about 1 in 350), simple blending cannot make a dip as deep as claimed, and the decisive test is whether the dips fall at that planet's transit times.

B. Data

8. Where does the data come from and what is in it? ZTF images from the IRSA archive. Per exposure: science image (38 MB), mask (19 MB), difference image (7 MB), PSF model (6 KB). A "unit" is field + CCD + quadrant + night.

9. Why query the metadata before downloading? It takes seconds, shows what exists (1,552 exposures, 898 r-band, 16.4% flagged, 40 usable nights), and lets us choose data on purpose; downloading the wrong 3.5 GB costs an hour.

10. How was the split decided and why by night? 8 train, 2 validation, 1 test (2019-02-08), 1 holdout (2022-06-17), written in configs/acquire.yaml before modelling. Frames of one night share stars, noise and artifacts; random splits would leak that.

11. Is it a problem that the test night is better than the training nights? It is a deliberate distribution shift: the test night is the sharpest and deepest, near opposition, so the most promising for discovery. We expect fainter sources than the model saw much of and read its scores with that in mind.

12. What makes your downloader safe to re-run after a crash? It is idempotent (existing files skipped) and atomic (written as .part, renamed when complete). It also retries with growing waits and records exposures that lack a product.

13. What is a unit and why are results per unit? One field + CCD + quadrant + night, e.g. 000618_c03_q4_2019-02-08. Linking needs frames of the same sky on the same night, and each quadrant has its own pixel grid and metadata.

C. Preprocessing and detection

14. What are the four files and what does the mask do? Science (tonight), difference (science minus aligned reference), mask (16 flags per pixel: saturated, dead, cosmic ray, ghost...), PSF (blur shape). We mask defects but not the ghost bit, because ghosts cover about 4% of the chip and masking them would hide real asteroids.

15. How do you get the reference image? reference = science - difference. ZTF already resampled and blurred the reference to match the science image, so no reprojection code is needed.

16. How is noise estimated and why robustly? SEP estimates the sky level and scatter in 64x64 boxes ignoring stars; for single images we use sigma = 1.4826 x MAD. Bright blobs inflate a plain standard deviation (15.1 vs 8.0 on an example frame).

17. Why keep only positive blobs? An asteroid is present tonight and absent in the reference, so it is a positive blob; negative blobs are things that faded or moved away.

18. Why did 1.5 sigma give fewer detections than 2 sigma? At the lower threshold neighbouring noise peaks touch and merge into large blobs, so the count drops (6,141 vs 7,764), and a faint asteroid next to a noise blob gets swallowed.

19. 7,800 blobs per frame, 173 with SNR > 5. Is that acceptable? Yes: detection is tuned for completeness (do not miss real things), classification for purity (throw junk away). Two steps, each doing what it is good at.

20. What is the combinatorics problem? 5 frames x about 8,000 blobs: all one-per-frame combinations are 8,000^5 = about 3 x 10^19. The CNN removes most junk first and the linker only tries combinations consistent with straight-line motion.

21. What is the WCS and why does it matter? The mapping between pixels and sky coordinates. Pointing shifts up to 12 px between exposures, so asteroids move in straight lines on the sky, not in each frame's pixels; linking must use sky-based common coordinates.

D. Leakage and exploration

22. Name the four kinds of leakage with an example each. Target (mag existed only for fakes), group (all tracklets from 4 images), shortcut (random bogus tracklets >= 222 px off a line), distribution shift (test night sharper/deeper).

23. What did the 100% -> 50% -> 99% experiment show? A model trained on easy data scored 100% on easy test data but 50% (a coin flip) on realistic near-miss tracklets; trained on realistic data it scored 99%. A perfect score was a symptom of a too-easy dataset, not of a good model.

24. What are hard negatives and why do they help? Negatives that look like the positives (here, near misses a few pixels off a line). The model learns most from them: accuracy was 99% with offsets of 3-10 px, 96% at 1-3 px and 89% at 0.5-1.5 px, which also shows how hard such cases are for position-only features.

25. How do you check that no night appears in two splits? check_split_leakage(a, b) lists groups appearing on both sides; it must return an empty list for train/validation, train/test and validation/test.

26. What would you do if a result looked too good? Ask what would have to be true of the data for it to be so easy; check features for target leakage, splits for shared sources, negatives for realism, and test on a different kind of data.

E. General ML and hygiene

27. What is overfitting and how does the split protect against it? Overfitting is memorising training noise. Only data the model has never seen shows whether it learned a general rule, so settings are chosen on validation and the test is opened once.

28. Why is accuracy a poor metric here? 3% positives: "always bogus" gets 96.8% accuracy with zero recall. Use recall, precision and average precision.

29. What does environment.yml give you? One command rebuilds the same software; without it "it worked on my machine" is unprovable (the laptop had at least 6 different Pythons).

30. What would you improve in the data stage? More fields and nights, especially near opposition; a formal learning-curve study (how performance grows with the number of nights); and an automatic check that archive quality flags and our mask agree.

31. "Did you write this code yourself?" Answer truthfully (see 00_Start_Here/07_AI_Use_and_Integrity.md): the project was developed with an AI coding assistant under Advik's direction; say what you re-ran, changed or extended in the data stage, then explain a step (for example the threshold table) without notes.
